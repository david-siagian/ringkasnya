# Workspace Rules

## CRITICAL GATE: Feature & Bugfix Review Board (Wajib Sebelum Coding)
- Setiap kali user meminta **fitur baru**, perubahan **alur pengguna / antarmuka**, atau **perbaikan bug (fixing)**, **WAJIB** baca dan jalankan skill `review-board` (`.agents/skills/review-board/SKILL.md`) **sebelum** memanggil `edit_file` atau `write_file`.
- Evaluasi di dalam *internal thought* **tidak sah** — hasil Review Board harus dicetak ke chat sesuai format skill `review-board` sebelum perubahan kode pertama dilakukan.
- *(Bypass: hanya lewati jika prompt secara eksplisit menyertakan `"skip review"`, `"no review"`, atau `"eksekusi"`.)*

## Planning & Documentation
- Setiap kali membuat atau memperbarui dokumen rencana (Implementation Plan / `/plan`), selain menyimpannya di Artifact Directory sistem, **wajib** juga menyimpan salinan file rencana tersebut (`PLAN.md`) langsung di dalam folder proyek aktif (`E:\MyApp\ringkasnya\PLAN.md`).

## Desain & UX (Ringkasnya)
- **Pendekatan Mobile-First**: Setiap desain UI dan UX wajib mengutamakan pendekatan *mobile-first* (rancang tata letak, tipografi, ukuran target sentuh, dan alur interaksi untuk layar mobile terlebih dahulu, baru ditingkatkan secara progresif untuk tablet dan desktop).
- **Kontras Cover & Header**: Kartu buku (`BookCard`) dan banner header pembaca (`BookReader`) menggunakan `book.coverGradient` dengan nuansa gelap (`800`–`950`) yang serasi dengan warna ilustrasi `.svg` masing-masing buku agar teks putih selalu kontras dan tidak bertabrakan.
- **Ilustrasi Sampul Buku (.svg)**: Setiap kali membuat atau meng-generate gambar sampul buku, buat dalam format vektor `.svg` saja (`viewBox="0 0 600 800"`, simpan di `public/images/covers/<slug>.svg` dan daftarkan di kolom `cover_image` tabel `books` di Cloudflare D1) dengan gaya editorial datar (ala Headway/Blinkist/Booksnap) alih-alih file raster `.jpg`/`.png`. Desain sampul harus sebisa mungkin menyerupai sampul buku aslinya (palet warna & motif visual khas) serta menyertakan **judul buku, subjudul asli, dan nama penulis** dengan posisi tipografi yang mirip seperti sampul buku aslinya (mengacu pada contoh `.svg` yang sudah ada). Khusus **subjudul di dalam sampul `.svg`**, wajib menggunakan **bahasa/subjudul asli buku** (jika buku aslinya berbahasa Inggris, tampilkan subjudul di sampulnya dalam Bahasa Inggris — hanya untuk teks di dalam sampul `.svg`, sedangkan kolom `original_title` & `tagline` di database tetap Bahasa Indonesia sesuai [`BOOK_CONTENT.md`](./BOOK_CONTENT.md)).
- **Navigasi & Transisi Smooth**: Jangan mengandalkan CSS `scroll-behavior: smooth` bawaan browser untuk hash scroll; gunakan `SmoothHashLink` dan `PageTransitionWrapper` (`src/components/SmoothNavigation.tsx`) agar scroll dan perpindahan halaman selalu mulus.

## Standar Konten & Durasi Baca
- **Konten Buku (`BOOK_CONTENT.md`)**: Setiap kali akan men-generate buku baru, memperbarui, atau menyunting konten maupun metadata buku di Ringkasnya, **WAJIB** membaca dan mematuhi seluruh standar di [`BOOK_CONTENT.md`](./BOOK_CONTENT.md) (serta menjaga sinkronisasi katalog di [`BOOKS_LIST.md`](./BOOKS_LIST.md)).
- **Konten Artikel (`ARTICLE_CONTENT.md`)**: Setiap kali akan men-generate atau menyunting artikel di Ringkasnya, **WAJIB** membaca dan mematuhi seluruh standar di [`ARTICLE_CONTENT.md`](./ARTICLE_CONTENT.md) (rubrik resmi, durasi baca 4–6 menit, struktur bagian & paragraf, integrasi `article-terms.ts`, serta ilustrasi SVG `240×240`), sekaligus menjaga sinkronisasi katalog di [`ARTICLES_LIST.md`](./ARTICLES_LIST.md).
- **Validasi Wajib Sebelum Migrasi Buku**: Jalankan `npm run validate:content -- migrations/<nama_file>.sql` untuk memastikan seluruh perubahan konten buku lolos aturan [`BOOK_CONTENT.md`](./BOOK_CONTENT.md) sebelum di-commit dan di-push.

## Operasional CLI (Windows)
- Jalankan `git push`, `npx wrangler`, `cf`, dan `gh` dengan `BypassSandbox: true` untuk menghindari `EPERM`/hang pada sandbox Windows.
- Jalankan `git add`, `git commit`, dan `git push` sebagai pemanggilan perintah yang **terpisah** (jangan digabung dalam satu baris perintah), agar approval prefix-matching tetap bekerja tanpa perlu meminta izin ulang untuk setiap commit message yang unik.
- Jalankan perintah `git` (`git add`, `git commit`, `git push`, `git checkout`, `git merge`, `git pull`) **langsung tanpa flag `-C <path>`** (karena *working directory* command sudah berada di root workspace), dan gunakan `git push` langsung untuk branch yang sudah memiliki *upstream* (atau `git push -u origin <nama-branch>` untuk branch baru) agar *prefix-matching* "Always Allow" pada `git push` cukup disetujui sekali.
- When interacting with Cloudflare, use the `cf` CLI unless the project has a Wrangler configuration file.

## Git Workflow & Branching
- **Branch `main` Hanya untuk Rilis (Production)**: Jangan melakukan commit atau push langsung ke `main` untuk pengerjaan fitur, bugfix, atau perubahan harian.
- **Branch `dev` sebagai Integrasi & Preview**: Semua perubahan fitur/bugfix digabungkan terlebih dahulu ke branch `dev`.
- **Alur Kerja Fitur / Bugfix / Lainnya**:
  1. Pastikan berada di branch `dev` terbaru (`git checkout dev`, lalu `git pull origin dev`), kemudian buat branch baru dari `dev` (misalnya `feat/<nama-fitur>`, `fix/<nama-bug>`, `docs/<topik>`, `chore/<topik>`). **Pengecualian**: jika ada permintaan fitur baru atau bug baru di sesi percakapan yang sama tetapi sebelumnya sudah ada branch yang dibuat di percakapan tersebut, **tetap gunakan branch tersebut** tanpa perlu membuat branch baru.
  2. Kerjakan perubahan pada branch baru tersebut (tidak perlu menjalankan `npm run build` maupun `npx test` secara lokal; untuk *refactor* besar yang menyentuh banyak file/tipe data, jalankan `npm run typecheck` sebelum push agar terhindar dari bolak-balik memperbaiki error di CI).
  3. Commit dan push perubahan ke branch baru tersebut (`git push -u origin <nama-branch>`). **Jangan langsung merge ke `dev`** — biarkan tetap di branch kerja tersebut terlebih dahulu.
  4. **Untuk perubahan yang perlu dipreview** (tampilan, logika aplikasi, bugfix, fitur baru, dll.): setelah `git push`, **jangan menunggu build Cloudflare selesai** — langsung kirim **URL preview perubahan** dengan format `https://<branch-slug>-app.ringkasnya.workers.dev` (di mana `<branch-slug>` adalah nama branch huruf kecil dengan `/` atau `_` diganti `-`, misalnya `feat/artikel-baru` → `https://feat-artikel-baru-app.ringkasnya.workers.dev`). **Jangan kirim URL dashboard Cloudflare (`dash.cloudflare.com`) maupun URL Git/PR GitHub.** Selalu tanyakan: `"Apakah sudah oke dan sudah bisa saya merge ke dev?"`. **Pengecualian (langsung merge ke `dev`)**: jika perubahan hanya berupa file aturan/dokumentasi `.md`, konfigurasi Cloudflare, atau konfigurasi/workflow GitHub yang tidak perlu diuji/dipreview, tidak perlu mengirim URL preview dan langsung lanjutkan ke langkah 5 (merge ke `dev`).
  5. Baru setelah user menjawab sudah oke / menyetujui, lakukan merge ke `dev` (`git checkout dev`, `git merge <nama-branch>`, `git push`), lalu pantau status workflow GitHub Actions (`.github/workflows/deploy.yml`) menggunakan `gh run list` / `gh run watch` untuk memastikan seluruh step (TypeScript Check, Build Project, dan Apply D1 Migrations) berjalan sukses.

## Deployment & Rilis
- **Auto-Deploy Cloudflare & GitHub Actions Aktif**:
  - **Preview (`dev`)**: Push/merge ke branch `dev` memicu workflow GitHub Actions (`CI & D1 Migrations`: typecheck, build, dan migrasi D1 preview) serta build & deploy Preview di Cloudflare Workers.
  - **Production (`main`)**: Push/merge ke branch `main` (khusus rilis) memicu workflow GitHub Actions (`CI & D1 Migrations`: typecheck, build, dan migrasi D1 production) serta build & deploy Production di Cloudflare Workers.
  - Tidak perlu menjalankan `npx wrangler deploy`, `npm run build`, maupun `npx test` secara manual setelah `git push`; cukup pantau eksekusi GitHub Actions hingga seluruh step dinyatakan sukses.
- **Auto-Push ke Branch Kerja (Tunggu Konfirmasi untuk Perubahan yang Perlu Preview)**: Setiap kali selesai mengerjakan perubahan, langsung lakukan `git commit` dan `git push` ke branch kerja (yang ditarik dari `dev`).
  - **Perlu Preview (tampilan, logika aplikasi, bugfix, fitur baru, dll.)**: **jangan langsung merge ke `dev`**. Setelah push berhasil, **langsung kirimkan URL preview perubahan** (`https://<branch-slug>-app.ringkasnya.workers.dev`, **bukan** URL dashboard Cloudflare maupun URL Git/PR GitHub) tanpa perlu menunggu build Cloudflare selesai, lalu selalu tanyakan `"Apakah sudah oke dan sudah bisa saya merge ke dev?"`. Lakukan merge ke `dev` dan push `dev` (serta pantau hasil GitHub Actions hingga sukses) hanya setelah user menjawab sudah oke, kecuali user meminta untuk tidak di-push terlebih dahulu.
  - **Tidak Perlu Preview (aturan `.md`, config Cloudflare, config/workflow GitHub)**: tidak perlu mengirim URL preview; langsung merge branch kerja ke `dev`, push `dev`, dan pantau GitHub Actions hingga sukses.

## Pengujian & Verifikasi
- **GitHub Actions sebagai Gerbang Utama**: Tidak perlu menjalankan `npm run build` ataupun `npx test` / `npm run test:e2e` secara lokal saat pengerjaan harian (cukup `npm run typecheck` opsional bila melakukan *refactor* besar lintas file/tipe data). Setelah push ke `dev` atau `main`, pantau workflow GitHub Actions (`gh run list` / `gh run watch`) untuk memastikan seluruh step berhasil.
- **Playwright Smoke Test (On-Demand)**: Uji browser (`npm run test:e2e`, mengacu ke `tests/smoke.spec.ts`) hanya dijalankan jika diminta secara eksplisit oleh user, dengan skenario minimal:
  - **Beranda (`/`)**: Zero `console.error` / `pageerror`, pencarian & filter kategori berfungsi, serta navigasi/smooth scroll ke katalog berjalan normal.
  - **Halaman Reader (`/buku/<slug>`, mis. `/buku/sapiens`)**: Toggle **Mode Kilat vs Mode Mendalam** berfungsi, bagian **Konsep Kunci** tampil normal, tombol salin kutipan & tema (`useTheme`) bekerja, serta endpoint `/api/health` merespons normal.
